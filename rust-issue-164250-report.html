0 · 问题：一段 safe Rust 打印出了乱码

下面是 issue 里的原始复现，通篇 safe Rust，没有用到 unsafe：

use std::sync::Mutex;
static KEPT: Mutex<Vec<Box<dyn std::any::Any + Send>>> = Mutex::new(Vec::new());
struct Q<T: 'static + Send>(Option<T>);
impl<T: 'static + Send> Drop for Q<T> {
    fn drop(&mut self) { if let Some(t) = self.0.take() { KEPT.lock().unwrap().push(Box::new(t)); } }
}
fn main() {
    {
        let l = String::from("hello world, this is long enough");
        let mut q = Q(None);
        q.0 = Some(&l);
    }
    let _z = String::from("XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX");
    let k = KEPT.lock().unwrap();
    println!("{}", k[0].downcast_ref::<&'static String>().unwrap());
}

程序想打印的是 l，也就是 "hello world, this is long enough"。实际输出：

O0（不优化）

XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX

看起来是后面变量 _z 的内容，原因见 5.4。

O2（优化）

UH..H..H..H..H.x.H.p.].%........

32 个乱码字节（xxd 显示，不可打印字节为 .）。第 5 节会用精简版说明，这是一段函数的机器码。

Rust 对 safe 代码有一个承诺：要么编译不通过，要么运行时不会出现内存错误（越界、悬垂引用等）。能守住这个承诺，语言就是 sound（健全）的。这里编译器接受了一段会读失效内存的 safe 程序，承诺被打破了，所以这个 issue 被标为 I-unsound。读失效内存属于未定义行为（UB）：语言对结果不作任何规定，可能打印乱码，可能崩溃，也可能“看起来正常”。

读完你会理解

  1. 为什么打印出的不是 l：一个已经过期的引用，在机器码里是怎么被读出来的（第 1、2、5 节）；
  2. Rust 用什么防止这种情况：生命周期是编译器的“有效期证明”（第 3 节）；
  3. 这份证明在哪里漏了（第 4 节）；
  4. 为什么漏了之后，程序运行时不会报错（第 6 节）。

为了让汇编短到能逐条读完，第 4 节起改用精简版 src/demo.rs：把 Mutex/Vec/Box/Any 换成一个全局指针槽位，取回时用了一处裸指针解引用。缺陷机制和症状与原始版相同；“safe Rust 也能触发”由上面的原始版证明。附录供想核验证据的读者使用。

赶时间？先看一页结论

① 漏洞在哪：编译期

struct Q<'a: 'static> 要求里面的引用活到程序结束。直接写 Q(Some(&l)) 会被 E0597 拒绝；先写 Q(None) 再写 q.0 = Some(&l)，这条约束就没有被检查。

② 汇编里的表现：没有可疑指令

&l 就是一条 lea 算出的栈地址。'static 转换没有生成任何指令。Drop 把这个地址 mov 进全局变量，随后 l 被 dealloc。之后读取时，CPU 和运行时都无从判断它已经失效。

③ 症状：取决于那块内存后来装了什么

O0 打印 32 个 X（与 z 复用了已释放的堆块一致）。O2 打印的 32 字节是格式化函数自己的机器码，因为旧栈槽被 println! 的参数复用了。ASan 报告 stack-use-after-scope。

Q(None)：约束只在这里检查→q.0 = Some(&l)：漏检→Drop：mov [KEPT], A→l 析构：dealloc(H)→按 String 读 A：[A+8]、[A+16]

1 · 内存基础：变量、地址、栈和堆

1.1 地址就是一个编号

可以把内存看成一个很长的字节数组，每个字节有一个编号，这个编号就是地址。在 x86-64 上，地址是一个 8 字节的整数。一个变量就是一段连续的字节；编译器决定它放在哪里。

  • 栈：函数的局部变量放在这里。每个函数调用有一块“栈帧”，编译器用 rbp 寄存器记住栈帧的基址，变量的位置写成 rbp-偏移，比如 rbp-0x20。函数返回时整块栈帧被收回。
  • 堆：大小在运行时才确定的数据放在这里，比如字符串的内容。由分配器管理：alloc 申请一块，dealloc 归还一块。

引用（&T）和指针在机器上就是一个地址，不带任何别的信息。

1.2 本文需要的全部汇编知识

[X]地址 X 处的 8 字节内存；[rax+8] 即“rax 指向的对象的第 2 个字” lea r, [X]只计算地址 X 放进 r，不读内存，相当于 Rust 的 & mov a, b把 b 复制到 a（寄存器或内存） rbp当前栈帧的基址；局部变量表示为 rbp-偏移 rdi / rsi / rdx函数第 1 / 2 / 3 个参数；rax 是返回值（x86-64 SysV 调用约定） call / jmp / ret调用 / 跳转 / 返回

1.3 一个 String 是两层内存

String 本身是栈上的 3 个机器字：容量、指向堆的指针、长度。字符内容在堆上。在本份 O2 产物中，变量 l 占 rbp-0x20 起的 24 字节。后文记号：A = l 的栈地址（也就是 &l 的值），H = 堆上字符的地址，F = 格式化函数 <&String as Display>::fmt 的地址（0x13eb0）。

1.4 两个会决定症状的事实

  • 释放不等于清零。dealloc 把这块堆内存还给分配器，内容原样留着。下一次申请同样大小的内存，分配器很可能把同一块交出去。
  • 作用域结束也不清零。变量离开作用域后，它占的栈字节也原样留着，但编译器可以把这段栈空间分给后面别的变量（栈槽复用）。这是正常、合法的优化。

所以，一个地址“还能读出东西”，不能说明它指向的对象还活着。

2 · 所有权与析构：谁在什么时候释放内存

  • 每个值只有一个所有者。let l = String::from(..) 之后，l 拥有那个 String，也就拥有那块堆内存 H。
  • 所有者离开作用域时，值被自动析构（drop）。String 的析构就是 dealloc(H)。
  • 同一作用域里按声明的相反顺序析构，后声明的先析构。
  • 类型可以实现 Drop 来自定义析构代码，析构时自动运行。
  • 引用不拥有对象。&l 是借用，复制它不会让 l 晚一点析构。
{
    let l = String::from("hello world, this is long enough");  // 先声明 l
    let mut q = Q(None);                                         // 后声明 q
    q.0 = Some(&l);
}   // 块结束：先 drop(q) → 运行 Q 的 Drop 代码；再 drop(l) → dealloc(H)

本例的 Q 有自定义 Drop：它把自己存着的引用放进全局变量 KEPT。块结束后 l 已经析构，KEPT 却还存着 l 的地址，这就是一个悬垂引用。

生命周期就是用来阻止这种情况的。

3 · 生命周期：编译器的“有效期证明”

Rust 不在运行时跟踪对象是否还活着，而是在编译时证明：每个引用被使用时，它指向的对象一定还活着。这份证明里用到的“有效期”就是生命周期。

3.1 这些写法怎么读

写法含义在本例中
'a生命周期参数，以 ' 开头的名字。它代表一段代码范围：“被引用的对象在这段范围内一定有效”。具体有多长由编译器推断，程序员只负责起名字和写约束。Q<'a> 中 'a 是“q.0 里那个引用保证有效的范围”。
'static内置的特殊生命周期，表示整个程序运行期间。字符串字面量、static 变量的引用都是 &'static。KEPT 是全局的，存进去的引用必须 'static，否则以后读到的可能是已释放的对象。
&'a String指向 String 的共享引用，编译器承诺这个 String 在 'a 范围内一直有效。&l 的真实生命周期只到内层块结束（第 32 行）。
'a: 'boutlives 约束，读作“'a 至少和 'b 一样长”。struct Q<'a: 'static>：'a 必须覆盖整个程序运行期。
impl<'a: 'static> Drop for Q<'a>在这个实现块内部，可以把 'a: 'static 当作已知事实使用。第 16 行能通过检查，靠的就是这个前提。

3.2 长可以当短用，短不能当长用

活得久的对象，在一段较短的范围里当然也有效；反过来不行。所以编译器自动允许把 &'static String 当作更短的 &'a String 使用，反方向则会报错。用术语说，&'long T 是 &'short T 的子类型。

static S: String = String::new();
let r: &'static String = &S;

{
    let local = String::from("x");
    let mut short: &String = &local;
    short = r;          // ✓ 长 → 短：S 活到程序结束，在这个块里当然有效
}

let mut long: &'static String = r;
{
    let local = String::from("x");
    long = &local;      // ✗ E0597：短 → 长，local 在块结束就析构了
}

3.3 协变：把“长可以当短用”推广到外层类型

如果一个类型里面装着 &'a T，比如 Option<&'a String> 或本例的 Q<'a>，那么 Q<'long> 能不能当 Q<'short> 用？

如果类型对这个引用只是存着、读出，答案是能。这种性质叫协变（covariance）：外层类型跟着里面的引用一起，“长可以当短用”。Option<&'a T> 和 Q<'a> 都对 'a 协变。

let a: Q<'static> = Q(None);
let b: Q<'short>  = a;     // 协变：允许把生命周期“缩短”（示意：'short 无法直接写在代码里）

直觉上这很安全：证明说“活到程序结束”，而你只依赖“活到块结束”，当然成立。（Rust 里也有不允许这样缩短的情况，比如通过 &mut T 访问的 T 是不变的，本文不涉及。）

本例有一点不同：Q 的声明带着约束 'a: 'static，即任何 Q<'x> 都要求 'x 覆盖整个程序。协变把 Q<'static> 缩短成 Q<'short> 时，得到的类型本身就违反了这条约束，按语言规则它不应该被接受。记住这一点，第 4 节就是在这里出的问题。

3.4 结构体约束，和 Drop 对它的依赖

struct Q<'a: 'static> 想保证：Q 里装的引用一定活到程序结束。impl<'a: 'static> Drop for Q<'a> 在实现块内部就把这条约束当作已知事实，所以 Drop 里可以写：

let  s        :  &'static String   =  s ;
│    │           │                     └─ 右边：上一行 if let Some(s) 绑定的旧 s，类型 &'a String
│    │           └─ 类型标注：要求新 s 是“整个程序期间都有效”的 String 引用
│    └─ 新变量 s，遮蔽（shadow）同名的旧 s
└─ 声明新绑定

这一行不改变值，新 s 和旧 s 是同一个地址。它要求编译器把这个引用当作 &'static String 来用。编译器接受的条件只有一个：能证明 'a: 'static。

  • 长变短，编译器自动允许：&'static String 可以直接当 &'a String 用：活得久的对象，在较短范围内当然也有效。这叫子类型（subtyping）。
  • 短变长，必须有证明：&'a String 当 &'static String 用，只有在 'a: 'static 成立时才行。这里的证明来自 impl 头的 'a: 'static：在实现块内部它是一个假设，编译器不会再去检查它。检查它的责任在创建和修改 Q<'a> 的地方，也就是 main 里。

本例的问题出在 main：q.0 = Some(&l) 本该检查却漏掉了，Drop 里的假设于是不成立。第 16 行本身符合类型规则，编译器不会在这里报错。

打个比方：引用像一个门牌号，生命周期是编译器替它签发的“有效期证明”。证明记在编译器的账本上，门牌上不写有效期。let s: &'static String = s; 是在账本上换了一张更长的证明，门牌号本身一个字都没改。

4 · 漏洞：换一种写法，检查就漏了

被拒绝（正确）

let l = String::from("hello");
let _q = Q(Some(&l));
// E0597

被接受（缺陷）

let l = String::from("hello world, …");
let mut q = Q(None);
q.0 = Some(&l);
// 编译通过

两段代码做的是同一件事：让 q 装着 &l。区别在于引用是构造时放进去的，还是构造后再赋值的。按照编译器实际产生的约束（附录 A0），它对右边这段代码的推理大致是：

  1. Q(None)：None 里没有引用，这个值的类型可以是 Q<'static>，满足 'a: 'static。✓ 检查通过
  2. let mut q = …：由于协变（3.3），变量 q 的类型可以比右边“短”。编译器给 q 推断出一个只覆盖内层块的生命周期，记作 'q，所以 q: Q<'q>。这时本该检查 'q: 'static。✗ 这一步漏了
  3. q.0 = Some(&l)：字段类型是 Option<&'q String>，只要求 l 活过 'q。l 确实活到块结束。✓ 检查通过
  4. 块结束 drop(q)：Drop 按 3.4 的假设，把 &l 当 &'static 存进 KEPT。
  5. 接着 drop(l)：KEPT 里留下悬垂引用。之后的读取就是 use-after-scope（作用域结束后的访问）。
归结起来，'a: 'static 只在 Q(None) 被构造的那一刻检查过；协变把 q 的类型缩短之后，没有人再检查缩短后的类型是否仍然满足约束。字段赋值就从这个缺口把局部引用放了进去。

第 2 步的说法来自编译器的 NLL 约束输出（约束图和原文见附录 A0、附录 A），它说明了“哪条约束缺失”，但没有定位 rustc 源码中具体是哪段代码漏检。原始版用的是类型参数 Q<T: 'static>，T = &String，同样是协变加字段赋值的模式。

5.2 找不到“错误指令”：Rust 语义与机器码的逐项对应

Rust 中的语义O2 汇编里对应的东西说明
struct Q<'a: 'static> 的约束无指令这是编译期要满足的条件，编译通过后就不再存在。
Q(None)无指令写入 null 的动作被下一条覆盖，优化后删除。Option<&T> 用 null 表示 None，Some(A) 就是 A。
q.0 = Some(&l)lea rax,[rbp-0x20] / mov [rbp-0x28],rax就是“取地址、存起来”。缺陷从这里进入运行时：编译器本应拒绝，但生成了这两条指令。

每条指令单独看都没有错。这些指令只有在“A 指向一个活着的 String”这个前提下才组成正确的程序，而这个前提本该由编译期证明。证明有缺口，指令就照着错误的前提执行。

5.3 O2 的输出：程序打印出了“正在打印它的那个函数”的机器码

到 println! 时，A 处的 24 字节已经被复用成 fmt::Argument：[A] = &s，[A+8] = F（格式化函数地址），[A+16] 仍残留着旧长度 32。fmt 把 A 当 String 读，得到“字符指针 = F，长度 = 32”，于是把 F 开始的 32 字节写到标准输出。这 32 字节就是 fmt 自己：

这里 CPU 没有执行失效数据，而是把一段代码当成字符串读了出来。F 在正常流程里确实是格式化函数，它又被误当成了字符数据的地址。

5.4 同一缺陷，O0 与 O2 症状不同

O0：栈对象还在，堆块被复用

l 在 [rbp-0xa0]，z 在 [rbp-0x80]，两者栈槽不同。析构 l 不会清零它的 24 字节，所以读 [A+8] 仍得到旧的 H。但 H 已经释放，紧接着 z 申请了同样大小的 32 字节。

O2：栈槽被复用，指针字被覆盖

6 · 为什么运行时发现不了

6.1 生命周期在生成机器码之前就被擦除了

源码写出 'a、'static
→
借用检查（NLL）在 MIR 上求解所有生命周期约束，生命周期只在这一步用到
→
擦除生命周期所有 'a/'static 变成同一个“已擦除”标记
→
优化 MIR → LLVM IR引用就是 ptr
→
汇编8 字节地址

借用检查结束后，rustc 把所有生命周期擦除，后面的阶段看到的就是“一个引用”。所以：

  • 3.4 里的 let s: &'static String = s; 在 O0 和 O2 的汇编里都是 0 条指令；
  • &'a String 与 &'static String 都是 8 字节地址，内存里没有地方存“有效期”；
  • 泛型 Q<'a> 不论 'a 是什么，二进制里都只有一份 Q::drop。Rust 规定生命周期不能影响生成的代码，所以才能整体擦除。

逐层证据（借用检查用的 MIR → 代码生成用的 MIR → 汇编中第 16 行如何消失）见附录 A0。

6.2 运行时能查什么，查不了什么

检查项能否只看地址值判断本例中
空指针能：地址是否为 0O0 的 read_kept 有 cmp rax,0x0
对齐能：地址低 3 位是否为 0O0 的 read_kept 有 and rax,0x7
对象是否还活着不能：需要知道这块内存当前归谁，而这份信息只存在于编译期没有任何检查，A 照常被读取

因此借用检查一旦漏检，结果不是 panic 或报错，而是未定义行为：机器码照常执行，读到什么取决于那块内存后来被谁用了（5.4）。

6.3 ASan：额外加一层运行时记录，才能抓到

AddressSanitizer（ASan）是一种调试工具：编译时在每次内存访问前插入检查，并为每块栈和堆内存维护一份“影子内存”，记录它当前是否有效。普通构建没有这层记录，ASan 构建有。

用 ASan 运行原始 safe 版，报告 stack-use-after-scope：一次 8 字节读取，位于栈帧偏移 264；变量 l 占 [256, 280)。264 − 256 = 8，也就是 String 的第二个字（指针字），与 5.2 表中 mov rdi,[rax+0x8] 这类读取一致。ASan 栈未符号化，不能精确对应到非 ASan 二进制的某条指令。完整报告见附录 B2。

把前面几节连起来：
  1. 引用在机器上就是地址；对象析构后，地址和内存里的旧字节都还在（第 1、2 节）。
  2. 防止悬垂引用的唯一机制是编译期的生命周期证明（第 3 节）。
  3. #164250 是这份证明的一个缺口：'a: 'static 在构造时检查了，协变缩短类型后没有再检查，字段赋值把局部引用放了进去（第 4 节）。
  4. 缺口一旦放行，后面每条机器指令都“正确”：取地址、存全局、释放、复用栈槽、按旧类型读取（第 5 节）。
  5. 生命周期已被擦除，运行时没有任何防线，结果是未定义行为。O0 的 X 和 O2 的机器码，是同一个悬垂地址在不同内存布局下读到的不同内容（第 6 节）。

读取的是已经失效的 String 对象，而不是合法保存的字符串内容。字符串有两层存储：栈上的对象描述信息，以及它指向的堆缓冲区。栈槽未覆盖也不代表对象仍然有效。

O0：栈对象信息仍残留，堆缓冲区可能被后续分配复用

精简版汇编中，l 位于 [rbp-0xa0]，q 位于 [rbp-0x88]，后续 z 位于 [rbp-0x80]。14dce 调用 q 的析构，14dfb 随后调用 l 的析构，14e14 再创建同为 32 字节的 z。保存的输出与“l 的旧堆缓冲区被 z 复用”的解释一致；项目没有保存堆地址会话记录，不能把复用地址当作已直接观测的事实。

O2：失效栈槽被格式化参数覆盖，读出代码段内容

精简版 l 的 24 字节栈对象位于 [rbp-0x20, rbp-0x08)。在本份产物中三个字依次为容量、堆指针、长度；这是当前汇编布局，不能当作 Rust 的稳定 ABI。q 的 Drop 保存了 rbp-0x20。随后格式化参数复用同一栈槽：

原始版：在 Drop 中保存局部引用

Q<T: 'static + Send> 的析构函数把 T 装入 Box<dyn Any + Send>，保存到全局 KEPT。之后通过 downcast_ref::<&'static String>() 取回。装箱保存的是引用值，不会复制或延长被引用的 String 的寿命。

use std::sync::Mutex;
static KEPT: Mutex<Vec<Box<dyn std::any::Any + Send>>> = Mutex::new(Vec::new());
struct Q<T: 'static + Send>(Option<T>);
impl<T: 'static + Send> Drop for Q<T> {
    fn drop(&mut self) { if let Some(t) = self.0.take() { KEPT.lock().unwrap().push(Box::new(t)); } }

精简版：保留生命周期问题，缩短机器码

Q<'a: 'static>(Option<&'a String>) 把约束直接写成生命周期。析构时 let s: &'static String = s; 在声明约束下能够通过类型检查，然后把地址存进全局原子槽位。read_kept() 的裸指针解引用要求对象仍然有效；本例逃逸之后已经不满足该要求。

use std::sync::atomic::{AtomicPtr, Ordering};

// 一个全局槽位，存放 "&'static String"（用裸指针存，读时还原成 &'static String）
static KEPT: AtomicPtr<String> = AtomicPtr::new(std::ptr::null_mut());

// 结构体声明：'a 必须 >= 'static。也就是说 Q<'a> 里的引用"保证"活到程序结束
struct Q<'a: 'static>(Option<&'a String>);

impl<'a: 'static> Drop for Q<'a> {
    #[inline(never)]
    fn drop(&mut self) {
        if let Some(s) = self.0 {
            // 在 impl 的 where 子句 'a: 'static 下，这一行类型完全正确：&'a String -> &'static String
            let s: &'static String = s;
            KEPT.store(s as *const String as *mut String, Ordering::Relaxed);
        }
    }
}

#[inline(never)]
fn read_kept() -> &'static String {
    unsafe { &*KEPT.load(Ordering::Relaxed) } // 这里的 unsafe 只是把 Drop 里合法存入的 &'static 取回来
}

fn main() {
    {
        let l = String::from("hello world, this is long enough"); // 32 字节堆内存

        q.0 = Some(&l);               // 关键：通过"字段赋值"把短命引用塞进去，编译器没拦
    } // <- 析构顺序：先 q（Drop::drop 把 &l 当作 &'static 存走），再 l（释放堆内存、栈槽失效）

    let z = String::from("XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX"); // 同样 32 字节
    let s: &'static String = read_kept();
    println!("{}", s);               // 读的是已死的 l
    drop(z);
}

附录 B4 / 结论范围与环境信息

当前项目的实验材料证明：带有 'static 约束的结构体，可以在先构造 Q(None)、再对协变字段赋值的路径上接收局部引用；析构函数随后按声明约束把该引用保存到全局，造成对象离开作用域后继续被访问。
  • 原始复现完全使用 safe Rust。Mutex / Vec / Box / Any 只是保存和取回逃逸引用的载体。精简版用裸指针与一处 unsafe 缩短汇编，不能单凭精简版声称“全 safe 代码造成 UB”；原始版和 ASan 报告提供了这条证据。
  • 构造与字段赋值的检查结果不同。直接构造 Q(Some(&l)) 的对照组被 E0597 拒绝；先空值构造、后字段赋值的复现组已经生成可执行文件及运行输出。
  • 运行时出现真实的生命周期越界。ASan 指向原始版局部变量 l 的栈对象，报告 stack-use-after-scope。
  • 优化级别改变症状。O0 保存的输出是 32 个 X；O2 保存的输出是格式化函数的 32 字节机器码。两者都不能当作程序的合法输出承诺。
